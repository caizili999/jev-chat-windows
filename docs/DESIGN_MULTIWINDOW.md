# 多独立窗口监控 · 设计

> 状态：**设计定稿，待实现**。决策全部来自一次 `/grill-me` 访谈，每条都记录了「为什么」。
> 相关：[README 的界面说明](../README.md#界面说明)、[DESIGN.md](DESIGN.md)、
> [USAGE_KB.md](USAGE_KB.md)（关系与知识库怎么用）。

---

## 1. 要解决的问题

现在程序只能盯**屏幕上唯一可见的那个聊天**：一个 hwnd、一个 WGC 会话、一个「当前会话」。
用户想同时盯多个群 / 多个人，并且**三个会话都自动回复**。

## 2. 为什么只能走「多个可见窗口」这条路

「同时看到多个聊天」在物理上只有三条路，前两条已被排除：

| 路 | 结论 |
| --- | --- |
| 让程序**主动点会话列表**切来切去 | ❌ 点开即已读，会**清掉用户的红点**；还会跟用户抢鼠标、打断手动操作 |
| 读微信**本地数据库** | ❌ 已被封杀：PyWxDump 2025-10 收到律师函删库停更（最高只支持到 3.9.12.51）；2026-01 腾讯据 DMCA 1201 下架 30+ 个仓库。法律 + 杀软 + 一升级就失效 |
| 听**系统通知** | ❌ 微信 PC **不发** Windows 系统 toast（一直走自定义提醒小窗），`UserNotificationListener` 读不到；且未打包的 Python 程序本身就没有 package identity 用不了该 API |
| **微信自己的「独立聊天窗口」** | ✅ 4.0.5+ 正式特性（右键会话 → 在独立窗口中打开）。每个是独立顶层窗口 |

**结论**：用微信 4.0.5+ 的独立聊天窗口——用户手动开几个，程序就盯几个。
副作用是**不清红点**，也不需要任何新依赖。代价是用户要动手摆一次，且受屏幕大小限制。

## 3. 实测事实（在用户机器上跑探针得到的，不是推断）

| 测的东西 | 结果 |
| --- | --- |
| 独立窗口是不是独立顶层窗口 | 是。类名 `Qt51514QWindowIcon`，`Capture(hwnd)` 直接能截 |
| `capture.chat_area()` 的像素锚点 | **3 个窗口全部成功**，标注图肉眼核对：红线=消息区顶、蓝线=输入框顶、品红=左右边界。**一行都不用改** |
| `ocr.Reader.read()` 消息识别 | **3 个窗口全部正确**：群发言人名（`保安大叔`/`fish-openwechat`/`KK`）归属对，单聊 `name=None`，时间戳解得出。**一行都不用改** |
| `ocr.read_title()` 读头部 | **3 个窗口全坏**，返回 `'口'`/`'一'`。原因：独立窗口的自定义标题栏（⊙ 订阅号图标 + 最小化/关闭按钮）**落在 WGC 捕获的客户区内**，头部裁剪把它也框进去了，`read_title` 取「最靠上的一行」就取到了图标 |
| Windows 窗口标题 | **直接就是准确的会话名**：`老婆` / `1群` / `程序员烧烤🦞技术交流群v3.0`。比 OCR 准、免费、无延迟 → **会话名改从 `GetWindowTextW` 取** |
| 窗口标题 vs 现有 KB 联系人 | **一个都对不上**（见 §6.2，这是最危险的一条） |
| 单窗口一次完整 OCR | **1.3~1.6 秒**（比 README 写的 250~800ms 慢，独立窗口裁剪区更大） |
| 主窗口现在能否截到 | 否——它收托盘了（`160x28 @(-32000,-32000)`）。**但 3 个独立窗口照样截得到** → 意外收获：可以把主窗口收起来只留独立窗口 |

## 4. 目标行为（用户视角）

1. 在微信里右键几个会话 → 「在独立窗口中打开」，摆到屏幕上。
2. 程序**自动发现**这些窗口（不需要配置），每个窗口算一个独立会话。
3. 每个窗口各自识别消息、各自生成候选、各自的会话标签页显示。
4. 每个会话**单独授权**是否自动回复；新出现的窗口默认**关**。
5. 你在电脑前时它不抢你的焦点；你走开了它才自动发。
6. 同时来消息时**排队**，一次只发一个。

## 5. 架构

```
现在：  worker.run(q, hwnd, ...)     ← 启动时定一个 hwnd
            └─ Capture(hwnd) → 1 个 title → readers{title: Reader}

改后：  worker.run(q, ...)           ← 自己发现窗口，hwnd 不再由父进程给
            ├─ WindowWatcher：每 ~1s 枚举一次，得出「该盯哪几个 hwnd」
            └─ 每个 hwnd 一套：Capture + Reader + 会话名（来自窗口标题）
                队列里每条消息带上「哪个窗口来的」
```

**分层**：新模块 `app/windows.py` 只做「枚举 + 判断是不是聊天窗口 + 取会话名」，
**纯函数部分不依赖 Qt 也不依赖 ctypes**（`pick_chat_windows()`），所以能离线测。

**父进程**：`state` 里那 7 个「单值全局」要改成按会话。

| 单值 | 位置 | 改成 |
| --- | --- | --- |
| `state["chat"]` | `main.py:478` | 每个会话各自记，不再有「当前会话」这个全局概念 |
| `state["hwnd"]` / `state["area"]` | `main.py:423` | 按会话：`{title: (hwnd, area)}` |
| `state["auto_title"]` | `main.py:399` | **保持单值**（排队放进新的 `state["auto_queue"]`）——见下面的「实现订正」 |
| `state["busy"]` | `main.py:417` | 保持全局「一次只跑一个分析」，但排队队列按会话 |
| `state["rerun"]` | `main.py:345` | 改成队列（现在只能挂一个，第二个会顶掉） |
| `state["input_has"]` | `main.py:425` | 按会话（输入框有没有字是按窗口算的） |

**已经是按会话的、不用动**：`chats{}`（`main.py:36`）、`state["quiet"]`、
`state["batches"]`、`overlay` 的 `feeds/hers/targets`、知识库 logs、聊天记录 CSV。

### 5.1 实现订正（S1–S6 落地时改掉的三处）

设计是访谈时写的，实现时发现三处对不上，都以实现为准，理由记在这儿：

1. **`auto_title` 不该按会话。** 上面那张表原本写「按会话：`{title: 待发内容}`（否则第二个会顶掉
   第一个）」，但悬浮窗的倒计时**本身就是单例**——`_autoTimer` / `_autoText` 只有一份，
   第二次 `begin_auto()` 会直接覆盖第一次。也就是说「待发内容」天然只能有一个，
   把它做成 dict 只是把「谁被顶掉了」这件事藏起来。真正的排队放在新的
   `state["auto_queue"]`：**同一会话只留最新一条，不同会话各排一条**（D10），
   由 `pump_auto_queue()` 在倒计时空下来时推下一个。
2. **`find_main_window()` 的判断要跟旧代码一模一样。** 初版按「可见 + 标题是微信 + 尺寸够大」
   三条筛，但旧的 `capture.find_wechat_hwnd()` 是「可见 + 标题『微信』，否则取第一个可见的微信窗口」，
   **刻意不看尺寸**。收托盘的主窗口实测是 `160x28 @(-32000,-32000)`——尺寸过滤会把它筛掉，
   而它恰恰是老用户唯一的那条路。所以判据放宽成跟旧代码逐条对应（尺寸阈值只用于
   `pick_chat_windows()` 挑**独立聊天窗口**，不用来挑主窗口）。
3. **独立窗口不再每次都抢视图。** S6 之前「发现一个新窗口就 `set_chat` 过去」是用户唯一能看见
   新窗口候选的办法（`main.py` 的注释里就写着「S6 的会话标签页会把这一步换掉」）。有了标签页之后
   再抢就变成「开三个窗口、界面停在最后一个」。现在只在界面上**还没在看任何会话**时才切。

**`fill(hwnd, area, text)` 本来就收 hwnd + area**（`fill.py:59`，坐标从
`DwmGetWindowAttribute` 的扩展边界 + area 偏移算），所以「往指定窗口填字」这条机制是**现成的**，
不用新写——要改的只是「谁决定往哪个窗口填」。

## 6. 关键决策（全部来自访谈）

### 6.1 决策表

| # | 决策 | 取值 | 为什么 |
| --- | --- | --- | --- |
| D1 | 目标 | **三个会话都自动回复** | 用户明确选择 |
| D2 | 会话名来源 | **窗口标题**（`GetWindowTextW`） | `read_title` 在独立窗口上实测全坏；窗口标题更准且免费 |
| D3 | 监控集合 | **自动发现**可见的独立聊天窗口 | 独立窗口本来就是用户手动开的，天然是白名单，不用再配一遍 |
| D4 | 主窗口 | **独立窗口优先；一个都没有时回退到主窗口** | 守住「不开独立窗口的老用户逐字节不变」；避免同一会话算两遍 |
| D5 | 聊天窗口判据 | 可见 + 尺寸够大 + 标题不在已知非会话名单 + **能过 `chat_area()`** | `chat_area()` 是天然试金石：聊天窗有面板底色和分隔线，看图窗没有 |
| D6 | OCR 预算 | **只 OCR 画面有变化的窗口** | `capture.py:144` 已经在算这个 diff，可以白拿。用户 3 个窗口通常只有 1 个在动 |
| D7 | 授权粒度 | **按会话**，新窗口默认**关**；群里默认要求 @我 | 109 人群 + 「不@我也回」+ 永远可见 = 持续刷屏，而且窗口在后台**用户看不见** |
| D8 | 焦点护栏 | `GetLastInputInfo`：**8 秒**没碰键鼠才发 | `fill()` 必须抢前台 + 移动鼠标，会打断用户打字。这条恰好把自动发送限定在真正需要它的场景 |
| D9 | 并发 | **排队**，一次只发一个 | `fill()` 抢焦点，并行必打架 |
| D10 | 队列合并 | **同一会话只留最新一条**，不同会话各排一条 | 否则群消息轰炸会让队列无限增长 |
| D11 | 界面 | 悬浮窗加**会话标签页** | 界面本来就按会话隔离，加标签页是最小改动；每会话一个悬浮窗会互相抢位置 |
| D12 | 未配对窗口的提示 | **非模态提示条** + 知识库窗口里一栏「当前看到的窗口」 | 见 6.3：模态框会让主循环停死 |
| D13 | 自动发现是否建联系人 | **不建**，不碰知识库数据 | 想记历史/带关系备注，用户自己「存为联系人」 |

### 6.2 ⚠️ 会话名对齐（D2 的必然后果）

窗口标题跟现有 KB 联系人**一个都对不上**：

```
窗口标题 '1群'                     vs 联系人 '1群(4)Q'              → ✗
窗口标题 '程序员烧烤🦞技术交流群v3.0'   vs 联系人 '程序员烧烤技术交流群v3.0'  → ✗（差一个 🦞）
窗口标题 '老婆'                     vs 没有这个联系人                  → ✗
```

差在哪：`1群(4)Q` 里的 **Q 是 OCR 把标题栏的 🔍 搜索图标认成的字**，`(4)` 是成员数；
`程序员烧烤…` 那条是当初「存为联系人」时 OCR 把 🦞 丢了。
另外 `normalize_name('1群(4)Q')` = `'1群(4)q'`——**群人数后缀那条正则没生效**，
因为 `(4)` 不在字符串末尾。

**后果**：一旦改用窗口标题当 key，现有 98 条（程序员烧烤）/ 23 条（1群）/ 15 条历史会
**全部静默对不上**，首页突然显示「本轮未使用知识库」，用户只会以为功能坏了。

**解法**：知识库窗口里加一栏「当前看到的窗口」——列出每个被发现的窗口标题，
你点一下就能把它配到某个联系人（**把窗口标题写进那个联系人的别名**）或新建一个。
配好之后，主窗口和独立窗口两条路就统一了：同一个会话不管用哪种方式打开都是同一个 key。

### 6.3 ⚠️ 模态框会让主循环停死

`ov.after(50, tick)` 在 `tick()` 的**最后一行**（`main.py:645`），
而 `kb_ui.confirm()` → `MessageBoxBase.exec()` 是**模态**的。在 `tick()` 里弹模态框，
下一个 tick 永远不会被排上 → 父进程彻底停（子进程还在截图、队列一直堆积、没人消费）。

→ **任何后台触发的询问都不许用模态框。** 用 `InfoBar`（浮一下就走）或事后列表。

## 7. 安全护栏（自动发送是唯一不可逆的动作）

发之前**逐条**检查，任何一条不满足就不发，并把原因写进状态栏：

1. **重读窗口标题**，跟生成候选时的会话名比对——这是「往错群发消息」的唯一防线。
2. **窗口句柄还有效**（窗口没被关掉）。
3. **输入框为空**（复用现成的 `input_has_text`，`capture.py:87`）。
4. **该会话已授权**自动回复（D7）。
5. **用户不在操作**（D8）。
6. 保留现有的三条：每个会话第一批消息不发（`main.py:372`）、判断引擎关着时如实标注
   （`main.py:395`）、发完 2.5 秒回看输入框（`main.py:449`）。

## 8. 向后兼容（这个项目最硬的约束）

**没有独立窗口 = 行为逐字节不变。** 具体：

- 发现逻辑返回空集合 → 回退到主窗口（D4）→ 与现在完全一致。
- 按会话授权的新开关**默认全关**，且不覆盖现有的 `auto_send_dm/group/group_any`
  （老配置的语义照旧）。
- 新模块是新文件；`core/` 一行不改；`app/kb` 一行不改。
- 「老用户」的定义：不用独立窗口的人。

## 10. 明确不做的事

- **不主动点微信的会话列表**（清红点 + 抢鼠标）。
- **不读微信本地数据库**（法律封杀 + 一升级就失效）。
- **不装额外依赖**（不引入 `pywin32` / `uiautomation` / `winsdk`）。
- **不自动建联系人**（不碰用户的知识库数据）。
- **不做「无人值守 + 全群自动发」的默认值**——那必须由用户显式开。
