- **新增 [docs/DESIGN_MULTIWINDOW.md](DESIGN_MULTIWINDOW.md)（多独立窗口监控 · 设计）**，
  以及它的地基切片 **`app/windows.py` + `tools/check_windows.py`**。
  起因：用户要「同时监控多个群/多个人」并且**三个会话都自动回复**。
  先做了一轮访谈式设计（`/grill-me`），把路走窄到唯一可行的一条：
  **用微信 4.0.5+ 的「独立聊天窗口」**（右键会话 → 在独立窗口中打开），每个是独立顶层窗口。
  另外三条路都排除掉了，且都有证据：主动点会话列表**会清掉用户的红点**并抢鼠标；
  读本地数据库已被封杀（PyWxDump 2025-10 收律师函删库、2026-01 腾讯据 DMCA 1201 下架 30+ 仓库）；
  系统通知监听不通（微信 PC 不发 Windows toast，且未打包的 Python 程序没有 package identity）。
  **六个切片 S1–S6 已全部落地**：S1 窗口发现（`app/windows.py`）、S2 子进程多窗口采集、
  S3 父进程七个单值全局改成按会话、S4 按会话授权、S5 焦点护栏 + 排队 + 发前六道闸、
  S6 悬浮窗会话标签页 + 知识库窗口的「当前看到的窗口」配对栏 + 未配对窗口的非模态提示。
  仍然**不在 README 里声称能用**：三个窗口各自自动回复这一条还没有在真机上跑过完整链路
  （S2 的采集/OCR/坐标已在真机三个窗口上验证过），等实测通过再说
- **S2：`app/worker.py` 自己发现窗口，一个窗口一套 `Capture` + `Reader`**。
  `worker.run()` 的签名从 `run(q, hwnd, enabled, …)` 变成 `run(q, enabled, …)`——hwnd 不再由父进程给。
  队列里每条消息都带上「哪个窗口来的」：`("session", hwnd, 会话名, is_main)` / `("gone", hwnd)` /
  `("lines", 会话, …)` / `("area", 会话, rect)` / `("input", 会话, has)`。
  `is_main` 这一位不能省：父进程必须分得清「主窗口换了会话」和「独立窗口钉住一个会话」，
  而这两件事从 `(hwnd, 名字)` 里看不出来。**真机验证过**：两个独立窗口（`1群`/`老婆`）各自
  报出的 session/input/area/lines 都带着正确的会话名，群发言人归属正确，单聊 `name=None`
- **S3：父进程那 7 个「单值全局」改成按会话**。`state` 从 `chat/hwnd/area/auto_title/busy/rerun/input_has`
  变成 `wins{会话:(hwnd,area,is_main)} / input_has{} / rerun{} / auto_queue{} / chat / analyzing` 等。
  **一处刻意没有照设计文档改**：`auto_title` 保持单值。设计文档的决策表写的是「按会话：
  `{title: 待发内容}`」，但悬浮窗的倒计时本身是**单例**（`_autoTimer`/`_autoText`，
  第二次 `begin_auto` 会覆盖第一次），所以待发内容天然只有一个；真正的排队放在 `state["auto_queue"]`
  （同一会话只留最新一条，不同会话各排一条）。**回退路径逐字节不变**：没有独立窗口时
  `showing(title)` 等价于老代码的 `state["chat"] == title`
- **S4：按会话的自动回复授权**（`settings.auto_chat(title)` / `save_auto_chat`，默认**关**）。
  设置页那个开关只对**独立窗口**的会话出现——主窗口（回退路径）走的是全局那三个开关，
  凭空多一个开关只会让老用户以为自己的设置被改了。**两层必须都开**才可能自动发：
  全局那三个开关 + 这个会话自己的授权
- **S5：焦点护栏 + 排队 + 发前三道新闸**。`app/focus.py`（纯 stdlib）用 `GetLastInputInfo` 算
  「你多久没碰键鼠」，**8 秒**才算走开；`GetTickCount` 49.7 天回绕必须做 32 位掩码（不做的话
  回绕那一下会算出天文数字的「空闲时长」）。发之前逐条重查：窗口还在吗（`W.alive`）/
  标题还是那个会话吗（`W.title_of` 重读，这是「往错群发消息」的唯一防线）/ 你走开了吗；
  加上原有的「输入框是空的」「界面还看着它」「微信没切走」。任何一条不满足就不发，原因写进状态栏。
  排队保证**一次只发一个**（`fill()` 要抢前台 + 移动鼠标，并行必打架）
- **S6：界面**。悬浮窗首页多一行**会话标签页**（只在「有自己独立窗口的会话 ≥ 2 个」时出现，
  点一下只换悬浮窗在看谁、微信那边一个都不动）；知识库窗口的联系人页多一栏
  **「当前看到的窗口」**——把每个窗口标题配到某个联系人（写进它的别名）。这一栏不是锦上添花：
  会话名从 OCR 头部改成窗口标题之后，现有联系人一个都对不上（`1群` vs `1群(4)Q`，
  那个 Q 是 OCR 把 🔍 认成的字），不配一次那 98/23/15 条历史会**静默**对不上。
  另外补上设计里的 D12：**未配对窗口用非模态 `InfoBar` 说一句**，带一个「去配对」按钮直接
  把知识库窗口开到联系人页。**必须是非模态**——`ov.after(50, tick)` 是 `tick()` 的最后一行，
  在 tick() 里弹模态框会让父进程彻底停死（子进程还在截图、队列一直堆、没人消费）。
  提示只在「是独立窗口 + 有知识库 + 这个标题还没说过」三条都满足时才出
- **S6 顺带收掉一个行为**：独立窗口出现时不再每次都把悬浮窗切过去。S6 之前那是用户唯一能
  看见新窗口候选的办法（代码注释里就写着「S6 的会话标签页会把这一步换掉」）；有了标签页之后
  再抢视图就变成「开三个窗口、界面停在最后一个」。现在只在界面上**还没在看任何会话**时才切

- **实测得到三条反直觉的事实**（都写进了代码注释和设计文档，别再踩）：
  ①`capture.chat_area()` 的像素锚点和 `ocr.Reader.read()` 的**消息识别在独立窗口上完全可用**
  （3 个窗口全部成功，群发言人名归属正确），**一行都不用改**；
  ②`ocr.read_title()` 在独立窗口上**返回垃圾**（实测 `'口'`/`'一'`）——独立窗口的自定义标题栏
  （⊙ 订阅号图标 + 最小化/关闭按钮）**落在 WGC 捕获的客户区内**，头部裁剪把标题栏也框了进去。
  好在 **Windows 窗口标题直接就是准确的会话名**（`老婆`/`1群`/`程序员烧烤🦞技术交流群v3.0`），
  更准更免费 → 会话名改从 `GetWindowTextW` 取；
  ③**窗口标题跟现有 KB 联系人一个都对不上**（`1群` vs `1群(4)Q`、`程序员烧烤🦞…` vs `程序员烧烤…`），
  直接换 key 会让 98/23/15 条历史**静默对不上**——所以设计里加了「知识库窗口里配对窗口标题→联系人别名」这一步
- **`app/windows.py` 守住的向后兼容**：有独立窗口时主窗口**不参与**监控（同一会话否则会被算两遍），
  **一个独立窗口都没有时才回退到主窗口**——「不开独立窗口的老用户行为逐字节不变」全靠这一条。
  另外收托盘的主窗口实测是个 `160x28 @(-32000,-32000)` 的窗口而 `IsWindowVisible` 照样返回 True，
  所以尺寸阈值是必需的，不能只靠可见性

- **修：聊天历史会永久冻结在某个条数上不再增长**（用户报「一直显示还是 18 条历史，我明明一直聊天」）。
  `append_log()` 里那条「k==0 且跟上一屏毫无交集 ⇒ 判定用户往上翻 ⇒ 日志别动」的启发式，
  **分不清「往上翻」和「两次分析之间一口气涌进来一整屏以上的新消息」**——两种情况长得一模一样。
  这本来只是少记一屏，但它在跳过时**连「上一屏」标记都不更新**，标记就永远停在旧屏上，
  于是之后每一轮都零交集、每一轮都跳过，**日志从此再不增长**。实测：`知识库/logs/9b44cc66ed34.json`
  自 21:44 起 80 分钟一条没写，而同期聊天记录 CSV 一直写到 22:40（应用是活的）；
  日志停在 18 条 = 21:06–21:40 那批，之后 22:33–22:35 的 21 条一条都没进去。
  修法只有一行：跳过时**也把「上一屏」标记更新掉**，断掉卡死链。追加语义一行没改
  （第 ① 轮仍然按上游规则跳过，第 ② 轮平滑前进时就把整屏补上，最多晚一轮）。
  `tools/check_kb.py` 新增「大跳不卡死」那组回归（零交集跳一轮 / 下一轮必须恢复 / 反复大跳也跟得上），
  已自证：去掉这一行，它会以 `日志永久冻结了` 失败
- **修：首页那行「本轮未使用知识库」会撒谎**。原来只按「笔记 + 历史」两个条数判，0/0 就写「未使用」，
  于是三种完全不同的情况被压成同一句话：①真的什么都没识别到；②联系人命中了、但这一轮确实没有
  可补的内容；③联系人背景（关系/备注/摘要）**确实发出去了**却一个字不提。
  第②种最容易撞上——一个会话的历史**全都还显示在屏幕上**时，`history_for()` 的去重会把它们剔成 0
  （屏上内容本来就在上下文里，重复带一份只是白占预算），于是用户明明存了联系人、知识库里也躺着
  十几条记录，却看到「未使用」，只会以为功能坏了。现在分三态说：
  `本轮未使用知识库` / `本轮已识别到联系人，但没有可补的内容` /
  `本轮已带上：N 条笔记、M 条历史[、联系人背景]`（`set_context_info()` 多收 `background` 与
  `contact_matched` 两个可选参数，老调用点行为不变；有笔记/历史时原有的两个数一字不改）。
  **注入逻辑一行没动**——去重是上游行为，该修的是说法，不是做法。
  `tools/check_kb_ui.py` 补了这三态和「空白背景不算背景」的断言，并在 `check_main_wiring` 里用真的
  `build_knowledge()` 复现了用户那一轮（联系人命中 + 历史全在屏上 → 注入为空）
- **新增「知识库与联系人」**（对齐上游 `jev-chat-jarvis` v1.3 的知识库那一档，Windows 这边整块可选）。
  设置页多一张「知识库」卡：手写笔记（标题/正文/标签，可设常驻），给会话建联系人（关系/备注/别名），
  另有一个独立的管理窗口（`app/kb/ui.py`，是个顶层窗口——长文本编辑塞不进 440 宽的悬浮窗页面栈）。
  分析时按**会话标题精确匹配**联系人、按**标签或标题**在会话标题与**最近 6 条**消息里命中笔记，
  命中的内容以「背景事实」带进 prompt。上游的常数一个没改：`BUDGET_CHARS=1500`、`MAX_HIT_NOTES=5`、
  `MATCH_WINDOW=6`、`DEDUPE_MIN_LEN=4`、`MAX_LOG=300`
- **「不改动现有行为」是这一轮最硬的约束，做法是让知识库整条线在「没内容」时彻底隐形**：
  `Overlay(kb=None)` 时设置页那张卡、首页那行计数、「存为联系人」按钮**全部 hide**，
  几个离线工具（`preview_ui` / `check_auto_send`）构造 Overlay 时就是这么用的，界面跟以前一个像素不差；
  `main.build_knowledge()` 在没有 store 时返回 `None`，`core` 收到 `None` 时请求体跟加这个功能之前
  **逐字节相同**（这条由 `tools/check_kb_inject.py` 钉着：`set(state) == {"chat"}`）
- **`core/` 不能反向 import `app/`**（分层是单向的），所以交接面是显式的：
  `app/kb/context.as_knowledge(ctx)` 把对象摊平成 `{"background": str, "history": [{from,text}]}`，
  `core.questions.knowledge_parts()` 只认这个普通 dict，认不出的一律当「没有知识库」。
  四个新字段 `background` / `history` 是**请求体里的可选字段**，不带就完全不出现
- **`BACKGROUND_NOTE` 是刻意**有条件**追加的**（上游无条件追加）：没有背景时连题干都跟以前一字不差，
  有背景时才补一句「Facts given in background are provided context, not off-topic.」——
  这样既守住了「无库用户请求不变」，也没动那句已经校准过的题干
- **4xx 防御性重试**：带着 `background`/`history` 的请求如果被 4xx 拒了，**脱掉这两个字段再发一次**
  （题干本身不动）。无字段的 4xx 不重试，5xx 也不脱字段——只对「我们新加的东西可能不被认」这一种情况兜底
- **「记录聊天历史」默认关，且 0 是合法值**：关着的时候知识库照样能用（手写的笔记和联系人照常注入），
  只是不带历史。`kb_history_count=0` 表示「只记录、不注入」——两个控件各自看都正常，凑一起才静默失效，
  所以设置页那行提示会明确点破这种组合（`_kb_hint`）
- **一屏 = 一个序列，不是一个集合**（上游最绕的一段，照搬）：同一屏不重写、屏幕上翻不写、
  只有「日志尾部与这一屏的开头重叠 k 行」才追加 `S[k:]`。刻意留着一条上游的**死分支**没「修好」
  （`save_or_merge_contact` 里那个永远不成立的别名追加），并加了注释说明——擅自修好会跟上游行为分叉
- **名字归一化**：去零宽字符 + 去尾部群人数后缀（半角/全角都认）+ trim + 小写。
  正则用 `_safe_regex()` 包着，**引擎不认这种写法时降级成「只 trim + 小写」而不是让整个类炸掉**——
  一个正则编译失败不该把每一次分析都拖死。注意「去人数」用的是**交替**不是字符类
  （Android ICU 不接受 `[(...)]` 这种写法，为了两边一致就这么写）
- **预算裁剪的顺序是硬要求**：常驻笔记豁免；超预算先丢**最旧的历史**、再**整条**丢笔记（绝不截半条）。
  历史去重也一样有顺序要求：`recent_log().filter(不在屏上).takeLast(n)`——**反过来会让当前屏上的
  消息吃掉配额**（要 30 条实际只拿到「30 减去屏上那几条」）
- **写盘一律原子**（临时文件 + fsync + `os.replace`），坏文件改名留档成 `*.corrupt.<时间戳>` 而不是
  静默覆盖；**移不走的坏文件直接拒绝写入**（记进 `unreadable`，永不覆盖）。
  `KbStore` 用 `RLock`——因为 `counts()` 会再进 `_load_log()`，普通 Lock 会自己把自己锁死
